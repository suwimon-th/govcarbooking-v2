# สิทธิ์รายบุคคล — ทดลองบน local

เปิดด้วย `npm run dev:permissions` แล้วไปที่ http://localhost:3100/calendar?login=1

| บัญชีจำลอง | รหัสผ่าน | บทบาท |
| --- | --- | --- |
| admin-local | local-demo-123 | ADMIN จัดการสิทธิ์ |
| user-local | local-demo-123 | USER ค่าเริ่มต้น |
| reports-local | local-demo-123 | USER ได้รับสิทธิ์รายงาน |

แอดมินเปิด http://localhost:3100/admin/permissions เลือกผู้ใช้ ติ๊กส่วนงาน แล้วบันทึก
ใช้หน้าต่างส่วนตัวอีกหน้าต่างเข้าสู่ระบบ user-local เพื่อตรวจเมนูและการเปิด URL โดยตรง
ข้อมูลจำลองเก็บในหน่วยความจำและจะกลับค่าเริ่มต้นเมื่อปิดเซิร์ฟเวอร์ ไม่เชื่อมฐานข้อมูลจริง
เซิร์ฟเวอร์จำลองพอร์ต 54329 และเว็บพอร์ต 3100 ผูกกับ loopback เท่านั้น รองรับเฉพาะการทดลองสิทธิ์และบัญชีจำลอง ไม่ใช่ระบบจำลองงานรถครบทุกฟังก์ชัน

## พฤติกรรม

- รุ่น 2: 21 หน้าภายในใน 14 โมดูล เลือกทั้งโมดูลหรือเลือกหน้าหลัก/หน้าย่อยแยกกันได้
- เปิดส่วนงานหมายถึงอนุญาตการทำงานเดิมทั้งหมดในส่วนนั้น ไม่แยกดูอย่างเดียว/แก้ไข/ลบ
- ADMIN เข้าถึงทั้งหมดเสมอ และเฉพาะ ADMIN จัดการบัญชีหรือสิทธิ์ได้
- ไม่เคยตั้งค่า: USER/TESTER ได้ขอรถ ประวัติคำขอ ประเมินบริการ ข้อมูลส่วนตัว และเปลี่ยนรหัสผ่าน; DRIVER ได้ข้อมูลส่วนตัวและเปลี่ยนรหัสผ่าน
- บันทึกสิทธิ์ว่าง: ปิดส่วนงานที่กำหนดได้ทั้งหมด ไม่ย้อนกลับค่าเริ่มต้น
- ตรวจสิทธิ์จากฐานข้อมูลทุกครั้งที่ขอหน้าหรือ API ที่คุ้มครอง เมนูรีเฟรชเมื่อกลับมาโฟกัสหน้าต่าง
- การถอนสิทธิ์ไม่ลบข้อมูลที่โหลดไปแล้วออกจากหน้าจอหรือ browser cache ทันที
- API ร่วมบางรายการใช้ได้จากมากกว่าหนึ่งส่วน เช่น คำขอและคนขับใช้การตั้งค่าคิวร่วมกัน
- หน้าสาธารณะ (ปฏิทิน ข้อมูลรถ เบิกน้ำมัน แจ้งปัญหา ตรวจรถ ประเมิน) และลิงก์งานคนขับเดิมอยู่นอกขอบเขตการตั้งค่านี้

## ข้อจำกัดที่ต้องทราบก่อนนำไปใช้จริง

การแก้นี้คุ้มครองเส้นทางหน้าเว็บภายในและ API ที่จับคู่ใน lib/permissions.ts รวมถึง API จัดการสิทธิ์ซึ่งตรวจ ADMIN ซ้ำใน handler
หลายหน้าของระบบเดิมยังอ่าน/เขียน Supabase โดยตรงด้วย anon key การป้องกัน route จึงไม่ใช่การรับประกันสิทธิ์ข้อมูลทั้งหมด ต้องตรวจ RLS และย้ายการเขียนข้อมูลที่สำคัญผ่าน API ที่ตรวจสิทธิ์ก่อนใช้เป็นขอบเขตความปลอดภัยจริง โดยเฉพาะ profiles.role และ profiles.password
ตารางสิทธิ์ใหม่ปิด anon/authenticated โดยเฉพาะ ไม่เปลี่ยน policy ของตารางเดิม
ระบบเก็บรหัสผ่านเดิมยังไม่ได้ย้ายเป็น hash ในงานนี้

## ขั้นตอนสำหรับการนำโค้ดขึ้นระบบภายหลัง

1. สำรองฐานข้อมูล และตรวจ RLS ของตารางเดิมตามข้อจำกัดข้างต้น
2. สำหรับฐานข้อมูลใหม่ รัน scripts/create_user_access_permissions.sql แล้ว scripts/expand_user_access_permissions.sql ก่อน deploy โค้ด; ฐานข้อมูลปัจจุบันรันทั้งสอง migration แล้วเพื่อใช้งานบน local
3. ตั้ง SESSION_SECRET แบบสุ่มยาวอย่างน้อย 32 bytes แนะนำแยกจาก SUPABASE_SERVICE_ROLE_KEY; ถ้าไม่ตั้งจะใช้ service key ที่มีอยู่ลงลายเซ็น session
4. ตรวจ LINE_LOGIN_CHANNEL_ID ให้ตรง LINE Login channel (ใช้ prefix ของ NEXT_PUBLIC_LINE_LIFF_ID_DRIVER เป็น fallback)
5. Deploy หน้าและ API พร้อมกัน แล้วให้ผู้ใช้เข้าสู่ระบบใหม่ cookie เดิมใช้ข้ามการตรวจสิทธิ์ไม่ได้
6. ลืมรหัสผ่านเปลี่ยนเป็นติดต่อ ADMIN; การเข้าสู่ระบบ LINE และการผูกบัญชีต้องใช้ access token ที่เซิร์ฟเวอร์ตรวจสอบกับ LINE

อ้างอิงการตรวจ token LINE: https://developers.line.biz/en/reference/line-login/#verify-access-token

## การตรวจสอบ

`npm run test:permissions` ใช้ข้อมูลจำลองทั้งหมด ทดสอบ session ปลอม/หมดอายุ ค่าเริ่มต้น สิทธิ์ว่าง เปิด URL โดยตรง API ไม่อนุญาตผู้ใช้ทั่วไปแก้สิทธิ์ ป้องกันปิดสิทธิ์ ADMIN และฐานข้อมูลสิทธิ์ล้มเหลวต้องปฏิเสธ

ปรับชนิด searchParams ของหน้าบันทึกเลขไมล์สิ้นสุดให้เป็น Promise ตาม Next.js 16 เพื่อแก้ตัวขัดขวาง build ที่พบระหว่างตรวจงาน

/admin/reports เป็นทางเข้ารวมและส่งต่อไปหน้ารายงานแรกที่มีสิทธิ์
บัญชี/สิทธิ์ของผู้อื่นสงวนสำหรับ ADMIN เสมอ แสดงในรายการขอบเขตสิทธิ์ด้านล่างพร้อมหน้าสาธารณะและหน้าคนขับ

### การรักษาสิทธิ์เดิม

permission_version=1 ถูกแปลงเป็น 2 เพียงครั้งเดียว โดยสิทธิ์เดิมของโมดูลจะได้หน้าที่เคยเปิดได้ทั้งหมด บัญชีเดิมยังเข้าถึงข้อมูลส่วนตัว/เปลี่ยนรหัสผ่านได้เหมือนก่อน
migration ไม่เปลี่ยน updated_by หรือ updated_at ของการตั้งค่าสิทธิ์เดิม และรันซ้ำแล้วไม่คืนสิทธิ์ที่แอดมินถอนภายหลัง
การบันทึกใหม่ต้องส่ง permission_version=2 และเลือกหน้าย่อยอย่างชัดเจน สิทธิ์ว่างในรุ่น 2 หมายถึงปิดทุกหน้าที่กำหนดได้
การทดสอบอัตโนมัติครอบคลุมทุกหน้าภายในที่มีอยู่ เพื่อจับหน้าที่ไม่มีการจับคู่สิทธิ์เมื่อเพิ่มหน้าใหม่
